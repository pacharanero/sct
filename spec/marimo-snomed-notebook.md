# SNOMED-aware notebook workbench

Status: Exploratory product spec, not a replacement for `sct gui` and not an implementation commitment. Origin: lessons from a local, private Data Golf workbench in September 2026. This refines the older [marimo/Jupyter idea in issue #42](https://github.com/pacharanero/sct/issues/42) now that `sct-py` exists; it does not close that issue or promote it to the roadmap. There is no roadmap delivery item yet, so the [roadmap's exploratory-ideas policy](roadmap.md#exploratory-ideas) applies until a first slice has an owner and evidence of usefulness.

## Problem and product hypothesis

`sct` makes terminology fast and local, but its CLI, MCP, GUI and Python surfaces do not yet give a clinician and a trusted agent one place to jointly formulate a question, inspect concept sets, change a proposed rule, and see how the change affects data. Agents can generate standalone analyses faster than a person can read them. A code-only notebook can reproduce that imbalance; a visual terminology browser alone cannot show application-specific row reasoning. A SNOMED-aware marimo notebook might connect both without moving a mature solver into notebook cells.

The central interaction is: **question and rationale -> editable terminology expression -> artefact-pinned concept set -> externally supplied application rule -> bounded presentation of the change -> inspect the concepts behind the change**. A human and, where policy permits, an agent should be able to read the same source and results. This is a concept-set analysis and codelist-design surface, not a new definition of clinical truth, a patient-data store, or SNOMED content authoring. Any accepted codelist is persisted only through an explicit human action and the existing checked codelist path, never through a notebook-specific format.

## Relationship to existing `sct` plans

- [`sdk.md`](sdk.md) describes the shipped typed Rust engine and `sct-py` adapter. Use them for current-release lookup, lexical search, expansion, hierarchy and provenance; fill genuine capability gaps there rather than scraping formatted CLI output or implementing ECL again in Python. Python results are ordinary dictionaries and lists, so a notebook adapter must validate them into explicit local models rather than treating `dict[str, Any]` as a typed boundary.
- [Issue #42](https://github.com/pacharanero/sct/issues/42) proposed plain SQL as an interoperability layer with marimo and Jupyter veneers, and [issue #41](https://github.com/pacharanero/sct/issues/41) tracks DuckDB integration. The first notebook slice should instead prove the shipped `sct-py` semantic path. A later Jupyter veneer may reuse importable adapter code, and DuckDB may bridge application data, but neither becomes a second terminology engine or the source of ECL semantics.
- [`gui.md`](gui.md) and roadmap `R38` specify the planned search-first clinical knowledge atlas with reusable custom elements and a pluggable terminology adapter. The notebook is a **complementary write-and-test analysis surface**; `R38` remains the primary browse-and-understand GUI. Prototype an embedded concept inspector against the same semantics and later assess whether the planned atlas components can be reused. Do not turn `R38` into a marimo dependency by implication, or publish a component library ahead of its existing gate.
- [`ecl.md`](ecl.md) documents the shipped grammar and its gaps. The current evaluator accepts attribute groups but flattens them into a conjunction, so the notebook must reject grouped refinements until exact role-group semantics ship. Its first ECL slice is also gated on actionable parser/evaluator diagnostics crossing the Python boundary and annotation warnings reaching a structured adapter channel rather than process stderr. It must never guess, silently broaden, or silently narrow a set.
- `R25`'s module-aware, point-in-time reconstruction is not shipped: a current-release SDK lookup must never be labelled as an exact historical edition. Current Snapshot inactivation reasons and associations are not a chronological lifecycle, and their absence must be distinguished from history evidence not being loaded.
- Keep the canonical RF2 -> NDJSON -> derived SQLite path. Notebook, Python adapter and anywidget must not build a private RF2 import or duplicate terminology SQL. Native read operations open the DB read-only. [`output-boundaries.md`](output-boundaries.md) governs generated HTML, Markdown, JavaScript and code display; [`R87`](refset-discovery.md#r87-local-dataset-coverage) is the existing design gate for any local dataset-coverage helper.

## Jobs and first useful screen

The default view is one question, not an empty data-science canvas: the clinical intent and uncertainty at the top; expression and policy controls alongside a concept-set summary; aggregate effect on authorised local data below; evidence and provenance always accessible. A run is a proposal until separately accepted by its owning application. Clicking an aggregate should retain the question, filters, terminology release, application-defined strata and reason for inspection. Human-agent sessions use synthetic data by default.

1. Search a clinical phrase with the shipped lexical search, or look up a syntactically valid SCTID exactly, without losing the question. Present candidates for human selection rather than claiming the ranking identifies the clinically correct concept. Show the preferred term stored in the selected database, FSN, SCTID, active status, primary release identity and content fingerprint. A composite build records only its first source as the primary release; exact constituent releases require an external manifest, while source paths remain redacted. A semantic tag parsed from the FSN must be labelled as derived. Report locale, inactive-content policy and refset mode as `not recorded` unless an external build manifest supplies them; absence from an active-only database is not proof that a description was absent from the published release.
2. Write or paste an ECL expression, validate it, then run it explicitly against the **selected loaded artefact**. Editing must mark results stale rather than re-running an expensive expansion on every keystroke. Compare `added`, `removed` and `unchanged` SCTIDs against a reference expression and inspect a display-bounded sample. The UI must distinguish a display limit from the current SDK's full materialisation of `expand()`; it cannot claim a query deadline, cancellation or backend result bound until those exist. Show total, returned count, truncation, primary release identity and content fingerprint. If caching is introduced, show a cache key/status bound to expression, artefact fingerprint, options and engine version. Expression annotation text is not authority for concept identity.
3. Move from a concept to direct parents, a limited child list, loaded inferred attribute relationships, and current Snapshot inactivation status and associations. Show multiple direct parents and disclose every limit or omitted result; pagination, complete root routes and group-preserving attributes require new SDK contracts and must not be simulated. Do not render a force-directed whole-ontology cloud. Show a keyboard- and touch-accessible inspector, not hover-only navigation.
4. In a later slice, test whether a proposed concept-set change affects an application's row predicate where an authorised adapter exists. Keep terminology membership, clinical interpretation and row eligibility such as age, dates, labs and medicines separate. Follow `R87` for encounter keys, duplicate policy, field and combined denominators, matching mode and build provenance. Show only aggregate additions/removals and locally filtered cohorts; never treat an expansion-count change as a measured patient-answer change.
5. Review reproducibility using what can actually be known: source and reference expressions, adapter options, notebook/package and `sct` versions, release ID, canonical content and companion fingerprints, local digest of sorted result SCTIDs, and the actual query invocation. Original build argv, binary/database file hashes, locale and ingest policy are shown only when independently captured, otherwise as `not recorded`. Source paths and database paths are sensitive local metadata and must be redacted from exportable views. Distinguish local runs, externally submitted observations and estimates; never infer an external result that was not observed.

### Concept lens and hierarchy affordances

Render SCTIDs in result tables as selectable concept references with a short hover/focus preview of FSN, preferred term, activity and release. Selecting one opens a persistent inspector with direct hierarchy neighbours, loaded inferred relationships, current status/associations and membership in the current/reference expressions. The same inspector should be reachable by search and keyboard. Hover over tokens **inside** an ECL editor is a later editor-integration/custom-widget experiment, not a capability to assume marimo provides natively. It must recognise syntactically valid ECL concept references, not arbitrary numeric strings.

A release comparison should identify every database by primary edition/release and content fingerprint and state the alignment policy, not offer one ambiguous global `as-at` switch. A composite database claims exact constituent releases only when an external manifest records them. The difference between a published module-aware edition and a naive component cutoff must remain visible. Until `R25` exists and is independently validated, the notebook can compare separately loaded artefacts or clearly labelled approximations only; it cannot silently claim to reconstruct a historical edition.

## Architecture and boundaries

```text
user / trusted agent <-> marimo notebook (question, ECL editor, inspector, aggregates)
                                  |
                     schema-validating adapter
                                  |
                       sct-py -> typed Rust SDK
                                  |
licensed RF2 -> canonical NDJSON -> derived read-only SQLite

marimo notebook -> explicit authorised application adapter
                -> least-privilege external rule runner -> aggregate result
```

Use marimo's Python-file notebook format for diffable source; generated output is not embedded in that source, but static HTML, Markdown, output-bearing IPYNB/PDF/PNG, executed WebAssembly exports and session snapshots are persisted artefacts and must be governed separately. The first prototype can use `mo.ui.code_editor`, an explicit run button, search and tables whose data is limited before construction. Table pagination is presentation, not a query bound, and download must be disabled wherever persistence is forbidden. Use one serial `sct-py.Snomed` session per query worker; do not concurrently share its synchronous connection. Use a small, fully local `anywidget` only if a persistent concept inspector or editor-token interaction cannot be composed with standard marimo controls. Any reusable atlas element receives schema-validated data through an adapter; avoid a second browser-side query engine. If the Python SDK cannot express a required query, add a tested SDK method or isolate a temporary structured CLI adapter with explicit provenance rather than parsing prose output.

Keep experimental ECL as *data*, not dynamically generated Python source. Arbitrary Python predicates, raw SQL and user-authored code execution are outside the first slice. If later required, run them in a separate least-privilege process with explicit argv, staged read-only inputs, a scrubbed environment, no ambient credentials or network, resource/time limits, aggregate-only output and cleanup on success or error. A marimo cell or run button is not isolation. The initial notebook must not rewrite application modules, submit results, mutate external state, or persist candidate data. It owns presentation and temporary orchestration; an application-specific adapter owns its schema and predicate. No competition data, solver or scoring logic belongs in `sct`.

Term and encounter content is shown only to an authorised local user. Default application-data views contain aggregates, not patient or encounter identifiers; terminology views still contain SCTIDs. [marimo pair](https://docs.marimo.io/guides/generate_with_ai/marimo_pair/) can inspect live variables, execute code and manipulate the UI, so pairing is enabled only for explicitly authorised synthetic-data editor sessions. Running the notebook locally does not imply agent context remains local. A cloud-backed agent is a separate synthetic-only profile whose provider traffic and data policy are explicit; private sessions run without editor/pair capabilities.

Licensed terms, private rows and sensitive paths must not appear in distributed notebook source, sample outputs, exports, snapshots, tracebacks, logs, agent context, audit records or packaged widgets. A private-session launcher must leave every marimo auto-download format unset, disable table downloads, redact errors/provenance, hide client-side export affordances, and block snapshot/export routes at an outer policy boundary. Marimo 0.25 has no global export-denial switch, and these controls cannot prevent an authorised viewer from manually copying or capturing displayed data. A private session writes no licensed output to notebook source, `__marimo__`, caches, exports, logs or audit records; in-memory state is discarded on shutdown.

The zero-egress profile uses bundled assets and preinstalled dependencies, sets `MARIMO_SKIP_UPDATE_CHECK=1`, prohibits runtime package installation, pairing, remote AI providers, analytics and remote terminology calls, and runs under an egress-denying outer boundary. Any external terminology adapter requires a separate use case, release policy and rights decision. Distributed notebook/widget code remains `AGPL-3.0-or-later`; production SNOMED content and derived databases are separate licensed material and must not be bundled or redistributed unless that terminology licence permits it.

## Suggested validation slices

1. **Capability and concept lens:** on the committed synthetic RF2 fixture, look up `22298006` (Myocardial infarction) and `46635009` (Type 1 diabetes mellitus), then run lexical search. Render stored terms, active state, release and a display-bounded, keyboard-operable parent/child inspector. Cross-check the same build through Rust SDK, Python SDK and CLI. Confirm unavailable metadata/history is distinguishable from a loaded empty value and that paths are redacted from exportable provenance.
2. **ECL scratchpad:** edit two expressions, mark prior results stale, then request expansion explicitly. Show concept-set additions/removals and clickable concept references with total/returned/truncated state. Compare exact SCTID sets to the Rust SDK for supported constructs; reject an attribute-group expression and another unsupported construct before evaluation. Verify parse/evaluation details and annotation warnings cross the adapter boundary without relying on process stderr. Never infer row impact from set counts alone.
3. **Hierarchy honesty:** exercise multiple direct parents, an over-limit child set, inferred attributes and current associations. Verify the UI never presents one representative hierarchy path as the only lineage, flattened attributes as role-group-preserving definitions, a limit as complete pagination, or missing history evidence as no associations.
4. **Data bridge, later:** after the `R87` contract is resolved, plug in a synthetic dataset and external read-only rule runner. Independently verify unique-row/encounter aggregation, duplicate policy, field and combined denominators, filters, matching/release provenance and cleanup on success or error. The same fixture must give a deliberately different answer when the expression or rule changes.
5. **Trust and output boundaries:** use adversarial synthetic FSNs, preferred terms, queries, paths and application values containing markup, quotes, controls and newlines. Verify literal rendering, no values interpolated into JavaScript/`innerHTML`/inline handlers, no table download or persisted snapshot/export/cache/log/audit value, redacted tracebacks, and discarded in-memory state on shutdown. Under the zero-egress profile, monitor the browser, marimo process and any child process and observe no external requests. Confirm private sessions expose no pairing/editor capability and no private/licensed value reaches an agent context; test cloud-agent collaboration separately with synthetic data and authorised provider traffic.
6. **Human-agent usability and reuse:** with synthetic data, ask a clinician and an agent to inspect and correct the same deliberately flawed expression and row rule. Measure whether the human can locate the changed concepts and explain the changed aggregate without reading generated scripts. Compare this with the present CLI workflow, then compare the inspector contract with planned `R38` custom elements and choose reuse, adaptation or intentional separation for a measured reason.

Acceptance for the first useful slice is one local marimo notebook that moves from an editable supported ECL query to a release-labelled, display-bounded set diff and accessible concept inspector; records a reproducible SDK invocation and available provenance; rejects grouped/unsupported semantics; has structured actionable errors; and retains or exports no licensed output. It passes slices 1, 2, 3 and 5 on synthetic data. Encounter testing, agent access to non-synthetic sessions, codelist persistence, Jupyter/DuckDB veneers and component reuse remain separately gated. This spec does not authorise a new roadmap item or distribution channel.

## Reading and prior art

These are research leads, not implementation dependencies or endorsement. Read the original material before borrowing UI ideas, code or terminology content.

- [SNOMED International's translation notebook proof of concept](https://github.com/IHTSDO/snomed_translation_poc) - notebooks for concept sampling and relationship context; a precedent for notebook-based terminology analysis, not evidence of a collaborative ECL/encounter workbench.
- [DrivenData SNOMED challenge resources](https://www.drivendata.org/competitions/258/competition-snomed-ct/page/823/) and [`snomed_graph`](https://github.com/VerataiLtd/snomed_graph) - sample notebook for browsing/selecting concepts; the graph library explicitly does not implement ECL.
- [Ontoserver ECL notebooks](https://github.com/sophie-w/ONTOSERVER_api) - Jupyter examples expanding ECL through a remote FHIR terminology server; contrast with the proposed local `sct` backend.
- [ECLed: a tool supporting the effective use of SNOMED CT ECL](https://pmc.ncbi.nlm.nih.gov/articles/PMC12777381/) - 2026 paper on ECL authoring, live results, MRCM guidance, and a parent/child concept viewer. Study its small eight-participant usability survey and untested larger-dataset scalability rather than copying its separate Angular/Spring architecture.
- [CSIRO Shrimp/ECL Builder](https://ontoserver-wp.csiro.au/our-solutions/shrimp/), [`aehrc/ecl-builder`](https://github.com/aehrc/ecl-builder) and [`aehrc/ecl-lsp`](https://github.com/aehrc/ecl-lsp) - direct ECL composition/editor prior art, including Monaco and Web Component integration. `ecl-lsp` currently targets ECL 2.2; these projects' terminology-server assumptions must be checked and they are not semantic authority for `sct`.
- The current [SNOMED CT Expression Constraint Language specification](https://docs.snomed.org/snomed-ct-specifications/snomed-ct-expression-constraint-language) is the semantic authority; implementation and editor prior art do not override it.
- [SNOMED International terminology services](https://www.implementation.snomed.org/terminology-services) and [SNOMED CT Browser ECL examples](https://docs.snomed.org/snomed-ct-user-guides/snomed-ct-browser-guide/tips-and-tricks/ecl-examples) - reference jobs and ECL semantics; browser/server behaviour is an independent comparison point.
- [marimo code-editor input](https://docs.marimo.io/api/inputs/code_editor/), [table input](https://docs.marimo.io/api/inputs/table/), [anywidget support](https://docs.marimo.io/api/inputs/anywidget/) and [marimo pair](https://docs.marimo.io/guides/generate_with_ai/marimo_pair/) - candidate building blocks and trust boundaries, not a ready-made SNOMED integration. [Watching notebook source from another editor](https://docs.marimo.io/guides/editor_features/watching/), [exports](https://docs.marimo.io/guides/exporting/) and [session snapshots](https://docs.marimo.io/guides/exporting/sessions/) document the source/editing and persistence behaviour that the prototype must verify against its pinned marimo release.
